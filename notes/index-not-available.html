NOTE 02 · DSE SEARCH

ReadFailure: INDEX_NOT_AVAILABLE

A search read failed because a replica could not serve its index. This is not a timeout, and it is not proof the table is down. The coordinator asked one node for index results and that node refused.

The error

ReadFailure: received 0 responses and 1 failures
(INDEX_NOT_AVAILABLE=[/10.1.2.21])
error_code_map: {'10.1.2.21': '0x0002'}

0x0002 is the DSE Search request-failure code for INDEX_NOT_AVAILABLE. The address in the map is the replica that failed the search request. Anonymize it in tickets and notes. The value itself is not the interesting part.

Plain CQL against a table with no search index does not throw this. The query was a search read: a solr_query, a CQL query that DSE Search rewrote, or a driver call against a search-indexed table.

What it means

The coordinator got a failure instead of rows. Zero responses and one failure means it did not fall back to another replica for that attempt. The named node was expected to serve the search index and could not. Usual reasons:

  • The search core is not loaded on that node. Startup, a failed core load, or the core was unloaded.
  • The index is still building after a create, a reload, or a node replace. Search indexing is asynchronous.
  • The node is up for Cassandra and down for Search. UN in nodetool status does not mean the core is queryable.
  • The index was never built on that node after a bootstrap or replace_address.
  • The query landed on a node that does not host the search index. Wrong datacenter, search disabled, or incomplete rebuild.

Check, in this order

  1. Confirm the client statement is a search read. If it is ordinary CQL, this error is the wrong diagnosis.
  2. Check the named node, not the whole ring. nodetool status first. A node in DN or UJ explains the failure. A node in UN does not clear it.
  3. On that node, check the core. dsetool list_indexes and dsetool status. Then dsetool get_core_status keyspace.table for the table the client queried. You want to know whether the core is loaded and whether indexing is still running.
  4. Read the node log around the failure for core-load errors, resource limits, or an index build still in progress. The client error will not say which.
  5. Ask whether this node was recently replaced, rebuilt, or had search re-enabled. A new node does not inherit a queryable index from the dead host.

Fix

What you foundWhat to do
Core missing or failed to loadFix the load error in the log, then reload the core. Reloading before the cause is fixed just fails again.
Index build still runningWait. Do not rebuild a core that is already indexing. Tell the client to retry after the core reports queryable.
Node joined or was replaced, index never builtRebuild the search index on that node only. Do not rebuild the ring.
Node is Cassandra-only, or in a datacenter without searchFix placement or client routing. No core command will create an index the node is not supposed to serve.
Several search nodes fail the same wayStop treating it as one bad host. Schema, resource limits, or a bad reindex are cluster-wide until proven otherwise.

AppDev can retry the read once the core is loaded. A retry against the same unavailable index fails the same way. This failure does not mean the Cassandra replicas lost the row. It means the search path could not answer.

Do not

  • Run a cluster repair because a search core was down. Repair does not load a Solr core.
  • Replace the node because Search refused a query. Cassandra can be healthy on that host.
  • Raise the consistency level to get past it. The index is unavailable. A stricter read still needs a core that can answer.
  • Paste the raw address, keyspace, or application name into a public note.

Commands differ by DSE version. Confirm dsetool subcommands and the search-index CQL syntax against the version you run. This is a decision aid, not a procedure for a specific cluster.
